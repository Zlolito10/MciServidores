## Reglas cruzadas Storage → Firestore

Las reglas del candidato leen como máximo dos documentos distintos por evaluación: `users/{uid}` y el evento o la asignación correspondiente, en la base `(default)`. La documentación oficial exige habilitar la conexión entre productos y señala el coste/límite de esas lecturas. La lectura IAM registrada no encontró un binding incondicional de `roles/firebaserules.firestoreServiceAgent` para el agente de Firebase Rules (`service-PROJECT_NUMBER@firebase-rules.iam.gserviceaccount.com`), y no certificó permisos efectivos por otras vías. Este requisito mantiene el gate bloqueado. Esta revisión no añade ese rol ni interpreta el emulador como evidencia IAM. [Condiciones de Storage](https://firebase.google.com/docs/storage/security/rules-conditions#enhance_with_firestore), [permisos del rol](https://cloud.google.com/iam/docs/roles-permissions/firebaserules).

`affectedKeys()` incluye los campos añadidos y eliminados además de los cambiados. Las concesiones de reglas que coinciden se combinan con OR; por ello se retiró el fallback Storage y la concesión duplicada de escritura en `app_cache`. [Control de campos](https://firebase.google.com/docs/firestore/security/rules-fields), [comportamiento de reglas](https://firebase.google.com/docs/rules/rules-behavior).

## Comprobación reproducible del candidato estable

Con Auth, Firestore, Functions y Storage Emulator activos en loopback para `demo-mci-servidores`:

```powershell
node --test tests/release-rules.integration.mjs
npm run test:integration
```

La primera suite crea únicamente identidades y recursos con prefijo aleatorio propio, comprueba el hub y elimina sus recursos concretos. No reinicia servicios ni resiembra las cuentas existentes. Guarda estados HTTP y nombres de pruebas, sin tokens, cookies ni cuerpos privados, en `recovery/release-rules-validation.json`. La segunda suite conserva su semilla demo estándar; no debe apuntarse a producción.

Antes de liberar el paquete, ejecutar sobre el mismo árbol estable la suite Node, los 15 tests Python, TypeScript, resolución de rutas/imports JSX mantenidos, integridad del snapshot y el build explícito de producción en un directorio separado del preview. Comprobar que el manifiesto usa el proyecto correcto, no contiene destinos de emuladores, mapas de fuente, fixtures ni archivos privados, y que la versión/caché cambia con el artefacto. Un fallo o una evidencia externa ausente debe mantener el gate de preparación cerrado; ninguna de estas comprobaciones autoriza un deploy.

## Resultado agregado del candidato

La verificación final de `release:verify` pasa **266 pruebas Node, 15 Python y 67 subflujos de emuladores** (69 resultados Node contando los dos contenedores). Se recompilaron frontend y backend dentro de la misma verificación; sus hashes y las fuentes no cambiaron durante las pruebas. La evidencia está en `recovery/production-validation.json`. La comprobación de integridad del artefacto pasa; el control completo conserva `readyToDeploy:false` por los requisitos externos, sin presentarlos como fallos de las pruebas locales.

La última revisión visual observó dashboard, asistencias y eventos, y una foto de perfil sintética de 5×5 decodificada desde un blob autenticado. El control del navegador se interrumpió antes de abrir el detalle del evento; no se afirma una revisión visual completa. Reporte: `recovery/production-browser-review.json`.
